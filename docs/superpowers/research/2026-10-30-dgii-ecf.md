## 1. e-CF types, e-NCF structure, mapping from traditional NCF

- e-NCF = **13 alphanumeric positions**: letter `E` (serie) + 2 digits (tipo) + **10 digits** (secuencial). Valid from the authorisation date **until 31 December of the following year**; cannot be used after expiry. **[INF §7]**
- XSD `eNCFValidationType`: `pattern=[a-z0-9A-Z]{13}`, length 13 **[XSD e-CF 31]**. DGII examples print lower-case (`e310000000001`) in URLs and upper-case in the FAQ ranges (`E310000000001`); the system emits upper-case `E`.
- `TipoeCF` enumeration in every XSD: `31, 32, 33, 34, 41, 43, 44, 45, 46, 47` **[XSD]**. Names **[FMT header row]**: 31 Factura de Crédito Fiscal Electrónica; 32 Factura de Consumo Electrónica; 33 Nota de Débito Electrónica; 34 Nota de Crédito Electrónica; 41 Comprobante Electrónico de Compras; 43 Comprobante Electrónico para Gastos Menores; 44 Comprobante Electrónico para Regímenes Especiales; 45 Comprobante Electrónico Gubernamental; 46 Comprobante Electrónico para Exportaciones; 47 Comprobante Electrónico para Pagos al Exterior **[FAQ-T Q28 table]**.
- Mapping from the traditional series (same two-digit type code, Phase 2 GC-10): B01→E31, B02→E32, B03→E33, B04→E34, B11→E41, B13→E43, B14→E44, B15→E45, B16→E46, B17→E47. (B12 "Registro Único de Ingresos" has no electronic counterpart in the XSD list.)
- Credit/debit notes may reference traditional NCFs: `NCFModificado` is `AlfNum11a19ValidationType` (11–19 chars) and **[INF footnote 44]** states the modified NCF can be serie "B" with 11 digits, serie "E" with 13 digits, or series "A"/"P" with 19 digits. Spec §3.4.1 requirement confirmed.

### Pre-certification (TesteCF) sequences **[FAQ-T Q27–Q28; SRV "Descripción de Ambientes"]**
Every taxpayer enabled in TesteCF has, per type, 1–10,000,000 (`E310000000001`–`E310010000000`), except type 32 with 1–50,000,000. [SRV] (2026) says the expiry of these test sequences is **31-12-2028** (FAQ-T from 2024 said 31-12-2025); test order: first 31 and 33–47 accepted, then 32 and RFCE **[FAQ-T Q29]**.

### 2.2 Differences per type (diff of the XSD trees, 2026-10-30)
- **32 vs 31**: no `FechaVencimientoSecuencia`; `Comprador` children all optional (`RNCComprador?`, `IdentificadorExtranjero?`, `RazonSocialComprador?`); no `TotalITBISRetenido/TotalISRRetencion/...Percepcion`; no `Retencion` in items; `Mineria?` added.
- **34 (NC) vs 31**: `IndicadorNotaCredito` (required, replaces `FechaVencimientoSecuencia`); `TipoIngresos` optional; no `TerminoPago/TablaFormasPago/TipoCuentaPago/NumeroCuentaPago/BancoPago`; `Comprador` optional with optional children; items `1..10000`; `InformacionReferencia` **required** with `NCFModificado`, `FechaNCFModificado`, `CodigoModificacion` required and `RazonModificacion?` (max 90).
- **33 (ND) vs 34**: 33 has `FechaVencimientoSecuencia` and no `IndicadorNotaCredito`; otherwise like 34 (payment-table fields absent, `InformacionReferencia` required).
- **44 / 45** follow 31 (not diffed field-by-field here; the writer uses the per-type XSD file at validation time).

### 2.4 Content restrictions **[EMI "Restricciones de Contenido"]**
- Escape `" ' < > & © € ®` in ALFANUM content (standard XML entities / numeric refs).
- **No empty tags**: any unused optional tag must be omitted ("provoca rechazos").
- File name standard: `RNCEmisor + e-NCF + .xml` (e.g. `101672919E310000000001.xml`); RFCE same; ARECF/ACECF use `RNCComprador + e-NCF`.
- Characters in the QR `codigoseguridad` URL parameter must be percent-encoded (table of reserved chars given; base64 chars `+ / =` are in the table).

The XSD files carry no license text or copyright notice (first lines: `<?xml version="1.0" encoding="utf-8" ?><xs:schema xmlns:xs="http://www.w3.org/2001/XMLSchema">`). ## 3. Authentication (semilla / token) **[SRV "Autenticación"; FAQ-T Q9]**
- Flow: `GET {base}/{ambiente}/autenticacion/api/autenticacion/semilla` → XML `<SemillaModel><valor>…</valor><fecha>…</fecha></SemillaModel>` (schema `Semilla v.1.0.xsd`: `valor` string, `fecha` dateTime). Sign the whole semilla XML with XMLDSig (same rules as e-CF) and `POST {base}/{ambiente}/autenticacion/api/autenticacion/validarsemilla` as `multipart/form-data`, field `xml` (`type=text/xml`).
- Response JSON `{"token": "...", "expira": "yyyy-MM-ddTHH:mm:ssZ", "expedido": "..."}` (also XML `<RespuestaAutenticacion>`). Token is a JWT, valid **1 hour**; sent as `Authorization: Bearer {token}` (RFC 6750).
- The certificate's `SN` (serial-number subject attribute) must be the RNC/cédula/passport of the owner; the signer must be a delegate authorised for the RNC emisor (rejection message "El RNC del certificado no está delegado para realizar transacciones para el RNC: {rncEmisor}").

## 5. Digital signature **[FIRMA; EMI "Firmado de XML"]**
- XMLDSig **enveloped** signature appended as the last child of the root (`<Signature xmlns="http://www.w3.org/2000/09/xmldsig#">` — the DGII samples use the default namespace, no `ds:` prefix).
- `CanonicalizationMethod` = `http://www.w3.org/TR/2001/REC-xml-c14n-20010315` (inclusive C14N); `SignatureMethod` = `http://www.w3.org/2001/04/xmldsig-more#rsa-sha256`; `Transform` = `http://www.w3.org/2000/09/xmldsig#enveloped-signature`; `DigestMethod` = `http://www.w3.org/2001/04/xmlenc#sha256`; `Reference URI=""`; `KeyInfo/X509Data/X509Certificate` with the signing certificate. SHA-256 is mandatory; sign with `PreserveWhitespace = false`; the signed XML must never be altered afterwards.
- Certificate: "certificado digital para Procedimiento Tributario" issued by a Dominican trust-service provider (entidad de certificación) to the person who acts as **Usuario Administrador e-CF / representante**, linked to the company RNC **[CERT requisitos]**. Supplied as `.p12/.pfx` + password (the DGII sample code loads a `.p12`). **UNVERIFIED (not in the fetched docs):** the current list of approved providers (commonly cited: Avansi, Viafirma, Cámara de Comercio de Santo Domingo / Digifirma).
- **Código de seguridad** = "los primeros seis (6) dígitos del hash generado en el SignatureValue de la firma digital" **[SRV; INF §18.2.3; FAQ-T Q15–16]**. **COMMUNITY PRACTICE (dgii-ecf npm 1.9.2, `getCodeSixDigitfromSignature`)**: `substr(SignatureValue text, 0, 6)` — the first six characters of the base64 `SignatureValue`; this is what the plan implements. Because base64 may contain `+`, `/`, `=`, the QR URL must percent-encode the parameter **[EMI]**.
- OpenSSL 3 note (**operational, UNVERIFIED for the company's certificate**): `.p12` files protected with legacy RC2-40 encryption fail in `openssl_pkcs12_read()` on OpenSSL 3 unless re-exported with modern ciphers (`openssl pkcs12 -export ... -keypbe AES-256-CBC -certpbe AES-256-CBC -macalg sha256`). The upload screen must show a clear Spanish error and the ops checklist must mention the conversion.

## 6. Printed representation (RI) and QR **[INF §18; RI; SRV]**
Mandatory content and placement **[INF §18.2]**:
- Top-right: type of e-CF in words; e-NCF; **Fecha Vencimiento** of the sequence (for comprobantes con valor fiscal — *not* for nota de crédito electrónica nor factura de consumo electrónica, footnote 43); for notes: **e-NCF Modificado** and **Código de Modificación** in words.
- Top-left (emisor): nombre comercial, razón social, sucursal, RNC, dirección, municipio, provincia, fecha de emisión. Below-left: client name and RNC (optional for consumo < 250k, footnote 42).
- Centre (Decreto 254-06 art. 8, NG 06-18): cantidad, "E" indicator for exempt lines, descripción (NombreItem), unidad de medida in words, precio, ITBIS, descuento, valor; Subtotal gravado / exento; Total ITBIS; Total; discount description/percent/amount when global.
- Additional data **[INF §18.2.3]**: **QR code bottom-left**, ≥ 2 cm from the sheet edge, **minimum 22 × 22 mm with 3 mm margin**; QR **"versión 8"** is stated by DGII (see note); **Código de Seguridad** in words below the QR; **Fecha de Firma Digital** `dd-MM-yyyy HH:mm:ss`.
- QR URL (e-CF): `https://ecf.dgii.gov.do/{amb}/consultatimbre?rncemisor=…&rnccomprador=…&encf=…&fechaemision=dd-MM-yyyy&montototal=…&fechafirma=dd-MM-yyyy%20HH:mm:ss&codigoseguridad=…`. QR URL (consumo < 250k): `https://fc.dgii.gov.do/{amb}/consultatimbrefc?rncemisor=…&encf=…&montototal=…&codigoseguridad=…`. Parameter names are case-insensitive (DGII prints them both ways).
- Note on "versión 8": a QR version-8 symbol holds at most 152 bytes at ECC L; the e-CF URL above is ~190–210 bytes, so a strictly version-8 code cannot encode it in byte mode. The DGII FAQ links the generic version table; the RI models show auto-sized codes. **Decision**: generate with automatic version selection (≥ 8), ECC L, and verify by decoding in tests. Mark as a point to confirm during certification (RI validation step).
- Foreign currency RI: when printed in the foreign currency, add the currency code to the money labels **[INF §18.2.2]**.
- Contingency legend (offline mode) **[INF §19; CONT]**: "e-CF emitido en modalidad de Contingencia, el cual podrá ser consultado para su validez fiscal, a partir de las setenta y dos (72) horas."
- An RI of an e-CF not received by the DGII or rejected cannot support crédito fiscal **[INF §18]**.

## 7. RFCE — consumo < RD$250,000 **[RFCE; SRV; FAQ-FC]**
- Facturas de Consumo Electrónicas with `MontoTotal` **< RD$250,000.00** are **not accepted** by Recepción e-CF; the issuer must send a **Resumen (RFCE)** to `recepcionfc`. Facturas ≥ RD$250,000.00 go in full to Recepción e-CF.
- The full e-CF 32 XML must still be generated, signed and **kept** ("el contribuyente deberá conservar el e-CF extendido") and the issuer must offer the receiver a way to consult it (ConsultaTimbreFC covers this).
- RFCE structure (`RFCE 32 v.1.0.xsd`): `RFCE/Encabezado{Version, IdDoc{TipoeCF=32, eNCF, TipoIngresos, TipoPago, TablaFormasPago?}, Emisor{RNCEmisor, RazonSocialEmisor, FechaEmision}, Comprador{RNCComprador?, IdentificadorExtranjero?, RazonSocialComprador?}, Totales{MontoGravadoTotal?, MontoGravadoI1?, I2?, I3?, MontoExento?, TotalITBIS?, TotalITBIS1?, 2?, 3?, MontoImpuestoAdicional?, ImpuestosAdicionales?{ImpuestoAdicional(0..20)}, MontoTotal, MontoNoFacturable?, MontoPeriodo?}, CodigoSeguridadeCF}` + `Signature`. `CodigoSeguridadeCF` = 6 chars, the security code of the **signed e-CF 32** (first 6 chars of its SignatureValue).
- The RFCE response is synchronous (estado Aceptado / Aceptado Condicional / Rechazado, `secuenciaUtilizada`); there is no TrackId for RFCE. The QR of such an invoice uses ConsultaTimbreFC.
- Limit: 10,000 lines for consumo < 250k **[INF §18]**.

## 8. Sequences, annulment (ANECF), reuse rules
- Sequences are requested by the taxpayer in Oficina Virtual (menu Facturación Electrónica → "Solicitud de secuencias"); **UNVERIFIED** exact menu wording, not in the fetched docs. Validity: until 31 December of the year after authorisation **[INF §7]**.
- Never reuse a number. After a rejection, DGII tells whether the sequence may be reused (`secuenciaUtilizada=false`) — the plan still never reuses it (planner decision; avoids edge cases) and instead reports it through ANECF.
- **ANECF** (`ANECF v.1.0.xsd`): `ANECF/Encabezado{Version=1.0, RncEmisor, CantidadeNCFAnulados (sum), FechaHoraAnulacioneNCF dd-MM-yyyy HH:mm:ss}` + `DetalleAnulacion/Anulacion(1..10){NoLinea (1..10 sequential), TipoeCF, TablaRangoSecuenciasAnuladaseNCF/Secuencias(1..10000){SecuenciaeNCFDesde, SecuenciaeNCFHasta} (13-char e-NCF each), CantidadeNCFAnulados}` + `Signature`. POST to `anulacionrangos/api/operaciones/anularrango`. Rejections: "Las secuencias que está intentando anular han sido utilizadas", "El campo NoLinea no es válido, no cumple orden secuencial", etc. For type 32 the DGII checks both reception channels (≥ and < 250k).

## 9. Receiver role: services the EMITTER must host **[EMI "Estándar como Receptor Electrónico"; CERT]**
- Mandatory: HTTPS ("SSL"), traditional ports, internet-reachable, case-insensitive paths, domain not blacklisted. Services share the standard resource paths; only the host differs:
  - **Recepción** (mandatory): `POST https://{host}/{…}/fe/recepcion/api/ecf`, multipart `xml` (an e-CF), optional `Authorization: Bearer` when the taxpayer declared an authentication URL. Response: a **signed ARECF XML** (`ARECF/DetalleAcusedeRecibo{Version, RNCEmisor, RNCComprador, eNCF, Estado (0 = e-CF Recibido, 1 = e-CF No Recibido), CodigoMotivoNoRecibido? (1 Error de especificación, 2 Error de firma digital, 3 Envío duplicado, 4 RNC Comprador no corresponde), FechaHoraAcuseRecibo dd-MM-yyyy HH:mm:ss}` + Signature).
  - **Aprobación comercial** (mandatory): `POST https://{host}/{…}/fe/aprobacioncomercial/api/ecf`, multipart `xml` (an ACECF). Response: HTTP 200 satisfactorio / 400 insatisfactorio.
  - **Autenticación** (optional): `GET …/fe/autenticacion/api/semilla` → SemillaModel; `POST …/fe/autenticacion/api/validacioncertificado` → `{token, expira, expedido}` (UTC `yyyy-MM-ddTHH:mm:ssZ`).
- **ACECF** (`ACECF v.1.0.xsd`): `ACECF/DetalleAprobacionComercial{Version, RNCEmisor, eNCF, FechaEmision, MontoTotal, RNCComprador, Estado (1 = e-CF Aceptado, 2 = e-CF Rechazado), DetalleMotivoRechazo? (≤250, required when 2), FechaHoraAprobacionComercial}` + Signature. The receiver sends its ACECF both to the DGII (`aprobacioncomercial`) and to the emitter's `urlAceptacion` from the directory. DGII-side rejections: "Aprobación Comercial no es requerida para este tipo de e-CF", "No se encuentra un e-CF válido para esta aprobación comercial", "Factura no encontrada…".
- The URLs (Recepción, Aprobación, Autenticación optional) are declared in the certification postulation form and later in "URL Servicios Producción" and are published in the DGII directory (`consultadirectorio`). **UNVERIFIED:** required response time for the ARECF (not stated in the fetched documents; the standard implies synchronous response to the POST).

## 10. Certification process **[CERT; CERT-PSFE]** (Ley 32-23, Decreto 587-24, NG 01-2020)
Requirements: RNC active and up to date; OFV access; Alta NCF; digital certificate (Procedimiento Tributario) of the Usuario Administrador e-CF linked to the RNC; invoicing software.
1. **Solicitud** — form "Solicitud para ser Emisor Electrónico (FI-GDF-016)" in OFV → credentials for the *Portal de Certificación de FE*; free testing in **TesteCF** (pre-certificación) first.
2. **Postulación** — "Crear Postulación" → Emisor Electrónico; software data: Tipo de Registro, Tipo de Software (externo/interno), Nombre, **URL Recepción**, **URL Aprobación**, **URL Autenticación** (optional), Versión, Datos del Proveedor; "Generar archivo" → sign the XML (App Firma Digital or own tool) → upload.
3. **Pruebas de Datos** — download the DGII Excel *set de pruebas* (e-CF) → generate XML with the same fields in the same order → send to **CerteCF** recepción (`https://eCF.dgii.gov.do/CerteCF/Recepción`), consult results (`…/CerteCF/ConsultaResultado`); a Rechazado restarts the set. Then the *set de Aprobaciones/Rechazos Comerciales* (expected answers "OK" / "Error").
4. **Pruebas de Simulación** — e-CF from representative real data; then upload the **RI PDFs (≤ 10 MB)** for format validation ("Representación Impresa Aprobada/Rechazada").
5. **URL servicio de prueba / Pruebas de comunicación** — optional root-certificate validation; DGII sends e-CF to the taxpayer's reception URL → the taxpayer must answer ARECF; then DGII sends ACECF → "OK"/"Error".
6. **URL Servicios Producción**, **Declaración Jurada** (XML signed by the representative), **Verificación de estatus**.
7. **Certificación** — authorisation; OFV menu Facturación Electrónica enabled (contingencia, delegación, consultas, directorio).
- **With a certified PSFE [CERT-PSFE]**: same solicitud/postulación (Tipo de Software = proveedor externo, mandatory provider data), *no Pruebas de Datos nor Pruebas de Comunicación*: only **Pruebas de Simulación** (e-CF to CerteCF; RFCE for consumo < 250k in pre-certificación), URL producción, declaración jurada, certificación. The PSFE hosts the reception/approval URLs.
- Deadlines (Ley 32-23): **UNVERIFIED in the fetched documents** — the spec says the contadora must confirm; widely published calendar: grandes nacionales 15-05-2024, grandes locales y medianos 15-05-2025, pequeños/micro/no clasificados 15-05-2026 (COMMUNITY/press, not from DGII pages fetched today).

## 11. Contingency **[CONT; INF §19]**
- **Falta de conectividad** (offline/intermittent): issue e-CF offline, deliver the RI with the legend "e-CF emitido en modalidad de Contingencia, el cual podrá ser consultado para su validez fiscal, a partir de las setenta y dos (72) horas.", and send the pending e-CF to the DGII **within 72 hours** of reconnection (Decreto 587-24 art. 40).
- **Imposibilidad técnica de emitir e-CF**: declare "Entrada en Contingencia" (Total/Parcial) in OFV → emit traditional **serie B** comprobantes; max **15 calendar days**; after "Salida de Contingencia", send within **30 days** the replacement e-CF (CodigoModificacion 4 "Reemplazo NCF emitido en contingencia") **only to the DGII**, not to the receiver.
- **Contingencia de la DGII** (DGII systems down): store the e-CF and send when communication is restored; scheduled maintenance is announced on the portal.
