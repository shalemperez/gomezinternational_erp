> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. **Goal:** Issue invoices, credit notes and debit notes as DGII electronic fiscal documents (e-CF types 31/32/33/34, plus 44/45 for régimen especial/gubernamental clients) through a swappable `EcfProvider` — `DgiiDirectProvider` complete, `AlanubeProvider` (PSFE) structurally complete, `FakeEcfProvider` for tests and dev — with XML built from the official XSDs, XMLDSig signing with the company certificate stored encrypted, queued submission with retries and status polling, RFCE summaries for consumo < RD$250,000, printed representation with QR and security code, receiver web services (acuse de recibo, aprobación comercial), annulment of unused e-NCF sequences, a fiscal-mode switch `ncf → ecf` with cutover date, admin/certification screens and immutable storage of every XML and DGII response.

**Architecture:** The sales documents of Phase 2 stay the source of truth. `FiscalNumberingService` becomes the switch: in mode `ecf` it assigns 13-character e-NCFs from `ncf_sequences` rows of electronic types (E31…E47) scoped by environment. The issuing actions (`IssueInvoice`, `IssueCreditNote`, `IssueDebitNote`) call `EcfService::create()` inside their transaction, which builds a provider-independent `EcfDocumentData`, writes the XML, validates it against the official XSD, signs it (when the provider signs locally), stores the immutable file and an `ecf_documents` row, then dispatches `SubmitEcfDocument` after commit. Jobs talk to the provider only through `EcfProvider::submit/poll`; every request/response is persisted as an `ecf_transmissions` row plus a file. The receiver role is a set of public `/fe/...` routes used only in DGII-direct mode. All secrets (certificate `.p12`, its password, PSFE API key) live encrypted in the database and never reach Inertia props or the activity log.

**Tech Stack:** Phase 2 stack + `robrichards/xmlseclibs ^4.0` (XMLDSig, ARCH §1.2) + `chillerlan/php-qrcode ^5.0` (QR PNG via GD; also decodes in tests). PHP extensions already present on the dev machine and required in production: `dom`, `libxml`, `openssl`, `gd`, `mbstring`.

### GC-18 e-CF data conventions
- `fiscal_mode` on invoices/credit notes/debit notes: `'ncf'` (traditional), `'ecf'` (electronic), `'external'` (historical). An issued document keeps its mode forever. The `ncf` column holds the e-NCF (13 chars) in mode `ecf`.
- One `ecf_documents` row per electronic document (`document_type`/`document_id` morph); status enum `App\Enums\EcfStatus` = `pending` → `signed` → `sent` → `in_process` → `accepted` | `conditionally_accepted` | `rejected`; plus `cancelled` (cancelled before any send). Labels (Spanish): "Pendiente de firma", "Firmado, pendiente de envío", "Enviado a la DGII", "En proceso en la DGII", "Aceptado", "Aceptado condicional", "Rechazado", "Anulado sin enviar".
- Files are immutable: `EcfStorage::putNew()` refuses to overwrite; paths `ecf/{environment}/{yyyy}/{encf}/{file}` on disk `local` (`storage/app/private`); received documents under `ecf/received/{yyyy}/{rncEmisor}{encf}.xml`. Every provider call writes an `ecf_transmissions` row (request file path, HTTP status, decoded response, error).
- Environments: `test` (TesteCF), `cert` (CerteCF), `prod` (eCF). `ncf_sequences.environment` scopes electronic sequences; traditional B-series rows are always `prod`. A database may hold e-CF of **one** environment only (GC-20).
- Secrets: `ecf_certificates.p12_encrypted`, `ecf_certificates.password_encrypted` and setting `ecf.alanube.api_key` use Laravel's `encrypted` cast / `Crypt`; they are excluded from activity logging and never serialised to Inertia (controllers send only `has_api_key: bool`, certificate subject/serial/validity).
- All DGII-facing timestamps use `America/Santo_Domingo` (`CarbonImmutable::now('America/Santo_Domingo')`); stored `signed_at` is UTC like every other timestamp.

### GC-19 Provider contract
`App\Contracts\EcfProvider` (Task 5) is the only seam between the ERP and the fiscal authority. Actions and jobs never call `DgiiClient`, `Http` or Alanube directly; the receiver role and commercial approvals (DGII-direct only) use `DgiiClient` through `ReceivedEcfService`/`CommercialApprovalService`. `EcfService::provider()` resolves the implementation from setting `ecf.provider` (`fake` | `dgii` | `alanube`), default `fake` outside production; in production `fake` is refused at settings save (Task 11).

### GC-20 Environment safety
Switching `ecf.environment` is refused when `ecf_documents` rows of a different environment exist: message "Esta base de datos ya tiene e-CF del ambiente {label}; usa una instalación separada para certificación o pruebas." Certification runs on a staging deployment with its own database; production switches to `prod` before the first electronic issue. Test environments never receive production sequences: the sequences form stores `environment` = current `ecf.environment` for E-types.

5. **Public receiver endpoints must reject malformed, unsigned, duplicate or mis-addressed documents with the right ARECF code and never 500** → Task 13 test `the reception endpoint answers a signed arecf with the motivo code for invalid xsd, bad signature, duplicate and wrong buyer rnc`.

/** Self-signed RSA-2048 certificate exported as PKCS#12 (binary), subject serialNumber = RNC as the DGII requires. */
function fakeP12(string $password = 'secret', string $rnc = '131880738', int $days = 365): string
{
    $key = openssl_pkey_new(['private_key_bits' => 2048, 'private_key_type' => OPENSSL_KEYTYPE_RSA]);
    $csr = openssl_csr_new(['countryName' => 'DO', 'organizationName' => 'Gomez International SRL', 'commonName' => 'Prueba Gomez', 'serialNumber' => $rnc], $key, ['digest_alg' => 'sha256']);
    $cert = openssl_csr_sign($csr, null, $key, $days, ['digest_alg' => 'sha256']);
    openssl_pkcs12_export($cert, $p12, $key, $password);

    return $p12;
}

## Decisions taken by the planner (spec silent or ambiguous)

1. **Signing happens synchronously at issue time; only the HTTP exchange is queued.** The certificate is local, so the signed XML, security code, signing time and QR exist the moment the invoice is issued and the RI can be printed immediately (with the contingency legend until the DGII accepts). A DGII outage therefore never blocks invoicing (spec §3.4 "pendiente de envío").
2. **No certificate (DGII-direct) ⇒ issuing in e-CF mode is refused** inside the transaction, so no e-NCF is consumed. The owner must upload the `.p12` before switching the mode (enforced by Task 11).
3. **Electronic sequences reuse `ncf_sequences`** with the new `E` types and an `environment` column; B-series rows stay `prod`. Ranges are 10 digits (`unsignedBigInteger`).
4. **One environment per database** (GC-20). Certification and tests run on a staging deployment; production switches to `prod` before the first electronic issue. This avoids e-NCF collisions between TesteCF and production ranges.
5. **Security code = first six characters of `SignatureValue`** (community practice matching the DGII wording); confirmed during certification by the RI validation step.
6. **QR version auto** instead of the "versión 8" the DGII mentions, because version 8 cannot hold the URL; tests decode the QR to prove the URL survives.
7. **Rejected numbers are never reused**, even when the DGII says the sequence may be (`secuenciaUtilizada=false`); the operator issues a new invoice and the number is queued for ANECF annulment with the cancelled-before-send ones.
8. **Cancelling an e-CF invoice is allowed only before it was ever sent**; afterwards the correction path is a credit note (`CodigoModificacion 1` when it annuls the full amount, else `3`).
9. **Credit-note code**: `1` when the note equals the invoice total + debits, otherwise `3`; debit notes `3`. `RazonModificacion` = the reason label. `IndicadorNotaCredito` from the 30-day rule.
10. **Foreign-currency invoices** are converted line by line at the document rate and the e-CF totals are the sums of the converted lines (so the DGII squaring never fails); the original amounts travel in `OtraMoneda`. The invoice's `total_base` may differ from `MontoTotal` by rounding cents; the e-CF is the fiscal truth in DOP.
11. **Exempt vs. 0 %**: the ERP only has 18 %, 16 % and "Exento (0.00)" → `IndicadorFacturacion` 1, 2, 4. Tasa cero (3) is not produced (no such rate exists in the product catalog).
12. **Receiver role**: only the two mandatory services are implemented (recepción with signed ARECF, aprobación comercial inbound); the optional authentication service is not declared to the DGII. Received e-CF are stored and can be approved/rejected commercially; registering them as purchases is Phase 4 (spec §9 item 4).
13. **Commercial approvals we emit** go to the DGII first (mandatory) and then best-effort to the issuer URL from the directory; issuer failures are logged in `notes`, never fatal.
14. **Alanube** is implemented end-to-end against its public reference (endpoints, auth, payload keys, response fields); `informationReference` sub-keys and the webhook payload are marked UNVERIFIED and must be confirmed with sandbox credentials before choosing the PSFE path. RFCE is the PSFE's responsibility in that mode.
15. **Fake provider** is the default outside production and is refused in production by validation; its outcome is driven by the setting `ecf.fake.outcome` so UI/dev flows can simulate rejections and outages.
16. **Alerts**: immediate notification on rejection; daily sweep for documents pending beyond `ecf.pending_alert_hours` (default 24 h) flagged urgent at 48 h (DGII 72 h window); recipients = users with `fiscal.ecf.alerts`.
17. **E-types 41/43/47 (compras/gastos/pagos al exterior)** get enum support, XSD files and sequences screens now, but their builders live in Phase 4 with the purchase vouchers.
18. **No `ImmutableWhenIssued` on `ecf_documents`**: the row is a state machine; immutability is enforced on the files (`EcfStorage::putNew`) and by the append-only activity log.
